### 6. PRODUCTIVITY PATTERNS

#### Pattern: identical surface symptom, multiple lower-layer causes
Within roughly a day, “Karabiner totally stopped working” has mapped to at least two different root-cause classes:
- local CPU saturation
- device-path / pairing-state failure

**Action:** create a short triage checklist for future outages with the first branch:
1. Is the machine overloaded?
2. Is the keyboard still on the expected receiver path?
3. Does macOS still see the device through the same path?
4. Are simple modifications dead, or only complex shortcuts?

This is a concrete time-saver and reduces repeated deep-dives.

#### Pattern: pairing state is an invisible dependency
The shortcut layer makes the problem look like software breakage, but the real dependency may sit in receiver slot state and connection mode.

**Action:** add a small “input-path matrix” note to project docs:
- receiver slot
- active pairing method
- expected macOS visibility
- whether Karabiner simple mods work
- whether wake latency is acceptable

This makes future regressions diagnosable without reconstructing the hardware state from memory.

#### Warning: fallback can hide root cause
CGEventTap fallback is useful, but if enabled without explicit degraded-state signaling, it can blur whether the primary path is healthy.

**Action:** define fallback as a named degraded mode with clear entry/exit criteria and some observable state. Do not let it silently become the permanent path unless that becomes an intentional later decision.
